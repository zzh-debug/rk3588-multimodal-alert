# 项目二总体实施计划

> 建立日期：2026-08-27（Asia/Shanghai）<br>
> 当前状态：P2.1、P2.3正式关闭，P2.2温度处理已通过；P2.4.1解耦及P2.4.2a DMA-BUF源路径已通过板端门禁，下一步评估RKNN io_mem<br>
> 上游基线：项目一 `c140532b82723bdfe1396b51304f2dfe9c4c73e7`

## 1. 目标和事实边界

项目二在项目一已经验收的真实硬件接口上，实现可见光、热成像、人员检测、
跨模态确认、自动补光和网络视频输出。开发顺序固定为“时间和Buffer正确 ->
温度和映射正确 -> 推理和融合正确 -> 拷贝优化 -> 补光和推流 -> 整链可靠性”。

第一版明确不承诺：

- 像素级跨光谱配准；
- 4K tensor 推理；
- 复杂多目标跟踪；
- 端到端或全程零拷贝；
- H.265双码流；
- 没有参考仪器时的绝对温度精度、LED电流和温升结论。

## 2. 已具备的输入

| 输入 | 已验证契约 |
|---|---|
| 可见光 | IMX415 -> RKISP mainpath，3840x2160 NV12约30 fps，AIQ选择目标IQ并运行3A |
| 热成像 | MLX90640 `ZMLX` Meta v1，3400字节，两个Chess Subpage组成约8 Hz完整pair |
| 时间 | 可见光V4L2单调时间戳；热payload包含两个Subpage的ready/read-done单调时间戳 |
| 补光 | `/sys/class/leds/zzh:white:fill/brightness`，0..255；当前仅验收到32 |
| 系统库 | OpenCV 4.5.4、RGA 2.1、RKNN Runtime、MPP、FFmpeg、GStreamer、MediaMTX |

## 3. 目标数据流

```text
IMX415 NV12 -> VisibleCapture -> FrameLease -> RGA branches
                                             |-> 640x640 -> RKNN -> Detection
                                             `-> 1080p/OSD -> MPP -> RTSP

MLX90640 ZMLX -> ThermalCapture -> Temperature -> Calibration -> ThermalROI

Visible timestamp + Thermal timestamp + Detection
                  -> TemporalJoin -> Fusion -> AlertEvent -> LED state/OSD
```

## 5. P2.1详细设计

### 5.1 设备发现

- 遍历 `/dev/media*`，通过 media entity 找到连接自研IMX415链路的
  `rkisp_mainpath`，不使用固定video编号。
- 遍历 `/dev/video*`，使用 `VIDIOC_QUERYCAP`、driver名、Meta Capture能力、
  `VIDIOC_G_FMT`和`ZMLX` fourcc识别热节点。
- 启动报告打印最终设备、driver、card、格式、宽高、plane、stride、sizeimage、
  Buffer数量和timestamp flags。

### 5.2 时间语义

| 对象 | 事件时间 |
|---|---|
| 可见光帧 | V4L2 Buffer `CLOCK_MONOTONIC` timestamp |
| 热完整帧 | 两个Subpage `ready_timestamp_ns`的中点 |
| 热帧跨度 | 第二页ready减第一页ready，单独记录而不隐藏 |
| 采集到达时间 | DQBUF前后的应用单调时间，只用于调度延迟统计 |

匹配由8 Hz热帧驱动：在有界可见光窗口中寻找绝对时间差最小的帧。第一轮保存
完整分布，不用拍脑袋门槛删数据；理论最近30 fps帧不超过约16.7 ms，工程暂定
观察目标为P99不高于25 ms，最终窗口只依据真机基线冻结。

### 5.3 Buffer和线程

- `VisibleCapture`持有V4L2 MULTIPLANE MMAP Buffer；每个下游对象持有可追踪的
  `FrameLease`，最后一个消费者释放后才QBUF。
- `ThermalCapture`校验magic/version/size/flags/subpage顺序后复制3400字节，立即
  QBUF；热payload很小，不需要跨线程占用内核Buffer。
- 初始线程为可见光采集、热采集、匹配/统计和监督四类；所有线程可停止并join。
- 队列容量、过期窗口和策略可配置；至少区分过期、超窗、队列满、消费者慢、
  capture error五类丢弃原因。

### 5.4 输出和验收

每个匹配事件写入CSV：session、两路sequence、两路event time、signed delta、
absolute delta、热Subpage span、DQBUF latency和drop counters。结束输出JSON摘要：
count、P50/P95/P99/max、queue high-watermark、sequence gaps、每类drop和reopen。

顺序门禁：

1. 原生单测：乱序、等距、超窗、队列溢出、时间回退和停止；
2. 板端60秒：自动发现、格式、时间flag、退出回收；
3. 板端10分钟：约18000可见光帧和4800热pair，生成分位报告；
4. 100轮STREAMON/OFF，无fd、mmap或Buffer泄漏；
5. 人工慢消费者，队列保持上限且退出不死锁；
6. 复用项目一受控L1故障，收到EIO后关闭/重开并恢复配对。

## 6. 后续阶段关键决策

### P2.2

- Melexis API必须记录来源、版本和许可证，并使用板端NVMEM EEPROM与捕获的
  ZMLX黄金输入做离线单测。
- 正式映射采用刚性支架和限定距离。当前已确认D110/BAA、110°×75°；机械基线、
  标定距离和真实对应点必须在正式映射验收前记录，否则只称经验ROI映射。
- 没有参考温度计时只验证稳定性、连续性和相对热目标，不声明绝对温度误差。

### P2.3/P2.4

- 首个NPU基线使用SDK现有RK3588 YOLOv5s 640模型，只取COCO person类别，记录
  模型哈希和来源；公开前重新审查模型许可证和可分发性。
- RGA letterbox必须保存缩放和padding参数，检测框通过同一参数映射回原图。
- 首版先证明MMAP功能正确，再验证`VIDIOC_EXPBUF`、RGA import fd、RKNN
  io_mem和MPP import；每个fd都有唯一owner和明确释放点。
- `80346d92fc3a`已证明4K MMAP帧经顺时针90°纠正、RGA NV12到RGB和letterbox、
  RKNN推理、person-only后处理及4K坐标反变换可运行；30秒基线为28.187 FPS、
  端到端P95 39.648 ms。
- 当前推理仍在采集回调中同步执行，30秒出现49次可见光sequence gap；该结果
  达到P2.3暂定吞吐/延迟门槛，但不能冒充P2.4完成或“零丢帧”。

### P2.5/P2.6

- AIQ会调节画面亮度，因此补光判定不能只看NV12平均Y，还要结合Y分位、曝光和
  增益。状态至少包括OFF、DARK_PENDING、RAMP、ON、HOLD、COOLDOWN和FAULT。
- 第一版编码1080p H.264单路，应用使用MPP生成码流并通过libavformat发布到本机
  MediaMTX；不自行实现完整RTSP服务器。

## 8. 第一项实施任务

完成P2.0后立即实现 `p2_capture_sync`，不先接Qt、OpenCV、RGA、RKNN或RTSP。
只有P2.1把设备发现、时间语义、Buffer回收、队列边界和错误恢复全部跑通，才进入
温度与推理阶段。
