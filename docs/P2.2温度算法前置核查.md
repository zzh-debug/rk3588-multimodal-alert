# P2.2 温度算法前置核查

> 核查日期：2026-08-27（Asia/Shanghai）<br>
> 状态：前置资料已确认；温度算法代码尚未开始

## 1. 已确认的输入

| 输入 | 结论 |
|---|---|
| ZMLX payload | 项目一 ABI v1，3400 bytes；每个完整帧含两个Chess Subpage，每页768像素+64 auxiliary |
| frameData映射 | `pixels[0..767]`、`auxiliary[0..63]`、`control`、`subpage_id`可重建为Melexis 834-word frameData |
| EEPROM | 项目一 NVMEM只读provider，1664 bytes；黄金SHA-256 `cc4628409b57ca3137065b10fd40c684fcef9d16ab493ace882710ad490185b2` |
| 官方算法 | 参考资料 ZIP 含 `MLX90640_API.cpp/.h`，文件头声明 Melexis N.V. Apache License 2.0 |
| SDK | Buildroot已有OpenCV imgproc/calib3d；不依赖OpenCV即可先完成温度算法单测 |

## 2. 不能直接假设的内容

- EEPROM 1664 bytes 的真实内容必须从板端 NVMEM 导出并与黄金哈希核对；不把截图、
  参考资料或手工构造数组当作标定参数。
- 精确 BAA/BAB/FOV 未确认。BAA约110x75°、BAB约55x35°的资料范围只用于规划，
  不能写入正式标定配置或对外宣称覆盖关系。
- 没有参考温度计时，只能验证温度矩阵连续性、相对热目标和算法自洽，不能声明
  绝对摄氏误差。
- 项目一 Meta 的 `status/control/subpage_id` 是小端字段，API输入数组必须显式
  做端序转换；不能直接把 `__le16` 内存当作主机 `uint16_t`。

## 3. 第一个P2.2实现

建立 `ThermalFrame` 用户态类型和 `mlx90640_math` 库，输入为：

1. 1664-byte 大端 EEPROM；
2. 两个经过 ABI 校验的 Subpage frameData；
3. 发射率 `emissivity`、反射温度 `tr`、坏点策略和滤波配置。

输出为：

- `ta_celsius` 环境温度；
- 32x24 `to_celsius` 目标温度矩阵；
- 32x24 `image` 红外强度矩阵；
- 坏点修复和输入有效性统计；
- `subpage_span_ns`、计算耗时和参数哈希。

首版优先调用官方 `MLX90640_ExtractParameters`、`MLX90640_GetTa`、
`MLX90640_CalculateTo` 和 `MLX90640_BadPixelsCorrection`。官方源码只保留
算法实现，I2C函数由项目二适配层隔离，避免复制其 Raspberry Pi I2C 驱动。

## 5. P2.2板端门禁

| 门禁 | 内容 |
|---|---|
| EEPROM | NVMEM导出1664 bytes，哈希等于黄金值，解析无越界/NaN |
| Golden frame | 固定保存一对真实ZMLX Subpage，离线重复计算结果一致 |
| 连续性 | 真实板端至少600个pair，温度矩阵无NaN、无无限跳变 |
| 坏点 | 使用EEPROM声明坏点；修复前后统计和结果可追踪 |
| 发射率/反射温度 | 配置可版本化，改变参数会产生可解释的结果变化 |
| 绝对精度 | 只有接入参考温度计/黑体后才执行误差门禁；否则只报告相对稳定性 |
| FOV | 确认实物 BAA/BAB 丝印、机械基线和适用距离后，才开始区域映射 |

## 6. 下一步顺序

1. 从板端导出 NVMEM 和一对 ZMLX 原始帧，保存为私有证据并计算哈希；
2. 引入带 NOTICE 的 Melexis API，写端序/参数解析/NaN 防护单测；
3. 编写 `p2_thermal_math_probe`，先离线输入再板端实时输入；
4. 在确认 FOV 和固定支架后进入区域级跨光谱映射。
